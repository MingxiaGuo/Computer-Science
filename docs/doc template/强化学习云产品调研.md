## 1. 调研背景与目标

### 1.1 背景

随着大语言模型的发展，模型训练逐渐从预训练、监督微调扩展到强化学习后训练。

强化学习已经成为提升大模型推理能力、任务执行能力、工具调用能力的重要手段。

对于云计算平台而言，强化学习不仅意味着增加一种训练算法，更意味着需要提供一套新的训练产品能力，包括：

- 强化学习任务管理
- 算法和训练框架管理
- 数据集和奖励模型管理
- 分布式训练资源管理
- Rollout 推理管理
- Agent 运行环境管理
- 训练过程监控
- 模型评估和版本管理

因此，需要调研强化学习领域的产品形态和行业方案，明确现有机器学习云平台应该如何扩展。

### 1.2 调研目标

1. 当前强化学习云产品的市场发展情况如何？

3. 云厂商提供了哪些强化学习相关产品能力？

7. 第一阶段应该建设哪些功能，后续如何迭代？

## 2. 市场及产品发展趋势

### 2.1 强化学习应用方向

| 应用方向     | 典型场景          | 产品需求             |
| -------- | ------------- | ---------------- |
| LLM 后训练  | PPO、GRPO、RLHF | 强化学习训练           |
| 数学推理     | 数学题、逻辑推理      | 奖励评估、模型训练        |
| Agent 训练 | 工具调用、多轮交互     | Agent 环境、Sandbox |
| 代码智能     | 代码生成、代码执行     | 代码执行环境、结果评估      |
| 机器人      | 机器人控制、仿真      | 仿真环境、分布式采样       |
| 自动驾驶     | 决策和控制策略       | 仿真平台、策略训练        |

### 2.2 强化学习与传统训练产品的区别

这是产品设计中非常重要的部分。

| 维度   | 传统模型训练                | 强化学习训练                             |
| ---- | --------------------- | ---------------------------------- |
| 数据来源 | 固定训练数据集               | 数据集 + 模型交互生成数据                     |
| 训练方式 | 数据输入、模型计算             | 采样、奖励、策略更新循环                       |
| 核心组件 | Dataset、Model、Trainer | Trainer、Rollout、Reward、Environment |
| 计算资源 | 主要用于训练                | 训练 + 推理 + 环境执行                     |
| 训练流程 | 相对固定                  | 多轮动态迭代                             |
| 监控指标 | Loss、Accuracy         | Reward、KL、Throughput 等             |
| 任务管理 | 训练任务                  | 训练任务 + 分布式执行任务                     |
| 结果评估 | 验证集评估                 | 奖励评估、任务成功率等                        |

产品层面的关键差异：强化学习不仅需要训练算力，还需要推理算力和交互环境。

## 3. 用户群体及核心使用场景

### 3.1 目标用户

| 用户类型       | 主要诉求      | 产品能力             |
| ---------- | --------- | ---------------- |
| 算法研究人员     | 验证算法、开展实验 | 开发环境、算法配置        |

### 3.2 典型用户使用场景

场景一：大模型 GRPO 训练

用户选择基础模型、数据集、GRPO 算法和 GPU 资源，提交任务，平台自动完成 Rollout、Reward 计算、模型训练和权重更新。

场景二：Agent 强化学习训练

用户准备 Agent、工具、任务环境及奖励规则，平台提供 Sandbox 运行环境，支持 Agent 与环境交互并收集训练样本。

场景三：多机分布式强化学习训练

用户选择多节点 GPU 资源，平台自动创建分布式执行集群，执行训练和推理任务，并提供资源及训练状态监控。

# 二、产品调研与技术调研应该如何分工？

这两份报告可以相互引用，但不要混为一份。

| 对比   | 产品调研报告      | 技术调研报告       |
| ---- | ----------- | ------------ |
| 核心问题 | 产品应该提供什么    | 产品如何实现       |
| 研究对象 | 用户、场景、云厂商产品 | veRL、Ray、K8s |
| 重点   | 产品功能、交互、体验  | 架构、源码、机制     |
| 输出   | 产品能力地图、功能规划 | 技术架构、选型方案    |
| 结论   | 建设什么、优先级如何  | 用什么技术、如何实现   |

举一个例子：

产品调研问题：是否需要提供 Ray 集群管理功能？

产品报告应该回答：

- 用户是否需要感知 Ray 集群？
- Ray 集群是否需要用户手动创建？
- 集群是否能够跨任务复用？
- 集群的状态是否应该在控制台展示？
- 用户是否需要配置 Head 和 Worker？

技术报告才回答：

- RayCluster 如何创建？
- KubeRay Operator 如何管理？
- RayJob 和 RayCluster 如何选择？
- Ray 集群如何分配 GPU？
- 集群如何销毁和恢复？

这就是两种报告的区别。

# 四、我对这次强化学习云产品调研的建议

实际上，你这次的调研最值得深入的不是 veRL 本身，而是下面四个问题：

重点一

强化学习产品与传统训练产品的差异

重点研究 Rollout、Reward、Environment 为什么会成为新的产品能力，以及它们如何被用户配置和管理。

重点二

强化学习任务的资源管理模式

用户看到的是 GPU 数量、节点数量和训推模式，平台内部需要管理 Trainer、Rollout、Ray Cluster 等资源。

重点三

强化学习训练的产品闭环

从基础模型、数据、奖励配置，到训练、评估、Checkpoint 和模型部署，形成完整使用链路。

重点四

与现有云平台的融合

哪些能力复用，哪些能力新增，哪些能力应该由底层自动管理，而不是让用户感知复杂的技术细节。

最终报告的定位应该是：基于行业产品调研，明确强化学习云产品的产品形态、核心能力、用户使用流程和建设路线，并给出可落地的技术架构方案。

这样才是一份完整的云产品调研报告，而不只是一次 veRL 和 Ray 的技术学习总结。
