## 1. 项目背景与调研目标

### 1.1 项目背景

随着大语言模型技术的发展，模型训练方式逐渐从传统的预训练、监督微调向强化学习训练扩展。

强化学习（Reinforcement Learning，RL）通过模型与环境进行交互，根据奖励信号优化模型策略，使模型逐步提升推理、决策和任务执行能力。

尤其是在大语言模型领域，RLHF、PPO、GRPO、Agentic RL 等技术逐渐成为模型后训练的重要组成部分。

现有机器学习云平台已经具备算力空间、开发环境、模型训练、模型推理等基础能力，底层基于 Kubernetes 和 GPU Operator 实现 GPU 资源管理与任务调度。

为了进一步完善平台的模型训练能力，需要增加强化学习训练功能，提供从数据准备、强化学习任务提交、分布式训练到模型产出的一体化服务。

3. veRL 的架构设计、核心模块及运行机制是什么？
4. Ray 在强化学习分布式训练中承担什么职责？
5. 如何将 veRL 和 Ray 集成到现有 Kubernetes 机器学习平台？
6. 如何管理强化学习任务涉及的 GPU、Ray 集群及训练资源？
7. 如何支持单机、多机以及训推资源共置和分离等部署模式？

### 1.3 调研范围

## 2. 强化学习技术概述

### 2.1 强化学习基本原理

强化学习是一种通过智能体与环境交互，根据奖励反馈不断优化策略的机器学习方法。

核心组成：

- Agent：智能体，负责根据当前状态生成动作。
- Environment：环境，接收动作并返回新的状态。
- State：当前状态。
- Action：智能体执行的动作。
- Reward：环境对动作或结果给出的奖励。
- Policy：策略模型，决定智能体如何采取行动。

典型流程：

1. Agent 获取环境状态。
2. Policy 根据状态生成 Action。
3. Environment 执行 Action 并返回结果。
4. Reward Model 或规则计算奖励。
5. 训练算法根据采样数据更新模型参数。
6. 重复交互和优化，逐步提升模型能力。

### 2.2 大语言模型强化学习流程

LLM 强化学习通常包含以下阶段：

1. 数据准备：准备 Prompt、训练数据及相关环境。
2. Rollout：使用当前策略模型生成回答或执行任务。
3. Reward：根据规则、奖励模型或环境执行结果计算奖励。
4. Training：根据 PPO、GRPO 等算法计算损失并更新模型。
5. Weight Update：将更新后的模型权重同步到推理引擎。
6. Evaluation：评估模型效果，进入下一轮训练。

### 2.3 典型算法

| 算法        | 特点                        | 适用场景         |
| --------- | ------------------------- | ------------ |
| PPO       | Actor-Critic，包含策略和价值估计    | 传统 RLHF      |
| GRPO      | 通过组内相对奖励估计优势，不需要独立 Critic | 数学推理、LLM 后训练 |
| DAPO      | 在 GRPO 基础上进行多项训练策略优化      | 大模型推理训练      |
| REINFORCE | 基于采样结果进行策略梯度优化            | 基础策略优化       |

## 3. 主流强化学习框架调研

### 3.1 框架对比

重点考察以下框架：

- veRL：面向大语言模型强化学习的高性能训练框架。
- OpenRLHF：基于 Ray、vLLM 等组件构建的 RLHF 训练框架。
- NeMo RL：NVIDIA 提供的大模型强化学习训练框架。
- TRL：Hugging Face 提供的模型后训练工具库。

### 3.2 对比维度

| 对比维度  | 主要考察内容              |
| ----- | ------------------- |
| 算法支持  | PPO、GRPO、DAPO 等     |
| 分布式能力 | 单机、多机、多 GPU         |
| 推理引擎  | vLLM、SGLang 等       |
| 资源调度  | GPU 分配、角色资源管理       |
| 训推部署  | 共置、分离、同步、异步         |
| 扩展能力  | 自定义 Reward、Agent、环境 |
| 平台集成  | Kubernetes、Ray、任务管理 |
| 社区生态  | 文档、活跃度、案例           |

### 3.3 技术选型结论

建议优先选择 veRL 作为第一阶段强化学习训练框架。

主要原因：

1. 支持 PPO、GRPO 等主流算法。
2. 具有 Trainer、Worker、Rollout 等清晰的架构抽象。
3. 支持基于 Ray 的分布式任务编排。
4. 支持训练与推理资源的灵活组合。
5. 具备较好的扩展能力，便于后续接入 Agent 和 Sandbox 等能力。

## 4. veRL 技术架构分析

### 4.1 核心架构

重点研究以下模块：

| 模块             | 职责             |
| -------------- | -------------- |
| Trainer        | 管理强化学习整体训练流程   |
| Worker         | 执行具体计算任务       |
| WorkerGroup    | 管理一组分布式 Worker |
| Actor          | 策略模型训练         |
| Critic         | 价值模型训练         |
| Rollout        | 使用推理引擎生成训练样本   |
| Reward         | 计算奖励           |
| ResourcePool   | 管理训练角色的资源分配    |
| PlacementGroup | 管理 Ray 分布式资源放置 |

### 4.2 训练执行流程

重点梳理：

1. Trainer 初始化训练任务。
2. 通过 Ray 创建 Worker 和 WorkerGroup。
3. 根据 ResourcePool 分配 GPU。
4. Rollout 执行模型采样。
5. Reward 计算奖励。
6. Trainer 调度训练过程。
7. Actor、Critic 等角色执行参数更新。
8. 通过权重同步机制更新 Rollout 推理引擎。
9. 进入下一轮训练。

### 4.3 训推部署模式

需要重点研究：

- Hybrid：训练与推理共享资源的部署方式。
- Standalone：训练与推理独立部署。
- Colocated：训练和推理角色在资源层面共置。
- 分进程与同进程运行模式。
- 同步与异步 Rollout。

重点关注不同部署模式下的 GPU 分配、进程组织、通信方式及权重同步机制。

### 4.4 权重同步机制

研究内容：

- CheckpointEngine 的作用。
- Naive、NCCL、NIXL、HCCL 等传输方式。
- 训练侧权重导出。
- 权重分桶与传输。
- 推理侧权重加载。
- 权重更新完成后的版本切换。
- 共置与跨节点场景下的实现差异。

## 5. Ray 分布式计算架构分析

### 5.1 Ray 核心能力

Ray 为 veRL 提供分布式执行和资源管理能力。

主要包括：

- Ray Actor：提供分布式执行单元。
- Ray Task：执行分布式任务。
- Placement Group：管理分布式资源组合与放置。
- Resource Scheduling：进行资源调度。
- Object Store：提供分布式对象存储与数据传递。
- Fault Tolerance：提供一定程度的故障检测和恢复能力。

### 5.2 Ray 与 KubeRay 的关系

Ray 负责分布式计算和任务执行。

KubeRay 负责在 Kubernetes 中部署和管理 Ray 集群。

主要 CRD：

| CRD        | 职责                   |
| ---------- | -------------------- |
| RayCluster | 创建和管理 Ray 集群         |
| RayJob     | 创建 Ray 集群并提交 Ray Job |
| RayService | 管理 Ray Serve 服务      |

### 5.3 单机与多机部署

重点研究：

- 单节点 Ray Cluster。
- 多节点 Ray Cluster。
- Head Pod 与 Worker Pod。
- GPU 资源发现与调度。
- 跨节点通信。
- 节点故障及恢复。
- Ray Cluster 自动扩缩容。

## 6. 强化学习云平台整体架构设计

### 6.1 总体设计思路

基于现有 Kubernetes 机器学习平台进行扩展，不重新建设底层算力管理体系。

整体分为四层：

**第一层：用户交互层**

- 强化学习任务创建。
- 算法及框架选择。
- 数据集和模型选择。
- GPU 资源配置。
- 任务状态及日志查看。

**第二层：平台管理层**

- RL 任务管理。
- 训练配置管理。
- 资源申请与调度。
- 任务生命周期管理。
- 训练结果及模型管理。

**第三层：强化学习执行层**

- veRL Trainer。
- Ray Cluster。
- Rollout 推理引擎。
- Reward 模块。
- Agent / Sandbox 环境。

**第四层：基础设施层**

- Kubernetes。
- GPU Operator。
- GPU 节点资源。
- 容器运行环境。
- 分布式存储。
- 网络与监控。

### 6.2 核心架构设计

平台通过 RL Controller 管理强化学习任务，根据用户配置创建相应的 Kubernetes 资源。

任务执行时，平台负责创建或复用 Ray Cluster，随后提交 veRL 训练任务，由 veRL 完成训练流程编排。

训练产生的模型权重和 Checkpoint 保存至平台模型存储，训练完成后可进入现有推理服务流程。

### 6.3 关键设计问题

1. Ray Cluster 是在算力空间创建时启动，还是训练任务提交时启动？
2. Ray Cluster 是否需要跨多个训练任务复用？
3. Ray Cluster 的资源是否独占？
4. 如何保证 Ray Worker 和 GPU 节点的资源分配一致？
5. 训练和推理是否支持 GPU 共置？
6. 多机资源不足时如何进行调度和排队？
7. 训练失败后如何进行恢复？
8. 如何管理训练产出的 Checkpoint 和模型版本？

## 8. 资源调度与生命周期管理

### 8.1 资源管理

需要管理的资源包括：

- Trainer 资源。
- Actor / Critic 训练资源。
- Rollout 推理资源。
- Reward 计算资源。
- Agent / Sandbox 环境资源。

### 8.2 资源分配模式

第一阶段建议优先支持：

1. 单节点多 GPU。
2. 多节点分布式训练。
3. 训练与推理共置。
4. 训练与推理分离。

### 8.3 生命周期

建议将强化学习任务抽象为独立的业务资源，由平台控制器管理其完整生命周期：

创建任务 → 资源校验 → 资源调度 → 创建 Ray Cluster → 提交训练 → 训练监控 → 保存 Checkpoint → 任务完成 → 资源回收。

## 9. 单机与多机部署方案

### 9.1 单机方案

- 使用单节点 GPU 资源。
- 创建单节点 RayCluster。
- 通过 Ray 执行 veRL 训练。
- 训练与推理可根据显存情况选择共置或分离。

### 9.2 多机方案

- 通过 Kubernetes 调度多个 GPU 节点。
- 使用 KubeRay 创建多节点 RayCluster。
- 通过 Ray WorkerGroup 执行分布式任务。
- 通过 NCCL 等通信机制完成分布式计算。
- 使用共享存储管理模型和 Checkpoint。

### 9.3 部署方案对比

| 维度     | 单机    | 多机            |
| ------ | ----- | ------------- |
| GPU 节点 | 1     | 多个            |
| Ray 节点 | Head  | Head + Worker |
| 网络通信   | 节点内   | 跨节点           |
| 部署复杂度  | 低     | 高             |
| 适用场景   | 小模型验证 | 大模型训练         |
| 资源调度   | 单节点分配 | 多节点联合分配       |

## 11. 技术风险与待决策问题

| 风险            | 影响            | 应对措施        |
| ------------- | ------------- | ----------- |

| Checkpoint 丢失 | 训练无法恢复        | 持久化存储及定期保存  |

2. 是否支持 Ray Cluster 跨任务复用？
3. 是否采用独占 GPU 作为第一阶段资源管理模式？
4. 是否支持训练和推理共置？
5. 第一阶段是否只支持 veRL？
6. 是否需要平台统一管理 Agent Sandbox？

## 12. 调研结论

建议基于现有 Kubernetes + GPU Operator 架构建设强化学习能力，采用 veRL 作为第一阶段强化学习训练框架，使用 Ray 提供分布式执行和资源编排能力，通过 KubeRay 实现 Kubernetes 环境下的 Ray 集群生命周期管理。

第一阶段优先完成单机训练闭环，验证任务创建、资源分配、训练执行、Checkpoint 保存和模型产出。

在基础能力稳定后，逐步扩展多机训练、训推分离、异步 Rollout、Agent 环境和弹性资源调度等高级能力。

最终实现与现有机器学习云平台统一的任务管理、资源管理、模型管理和监控体系。

# 四、不同类型的调研报告，结构应该有所区别

不要每次都机械套用完整模板。不同调研目的，重点不同。

| 调研类型   | 核心关注点   | 推荐重点          |
| ------ | ------- | ------------- |
| 技术原理调研 | 技术怎么实现  | 原理、架构、源码、流程   |
| 框架选型调研 | 选哪个框架   | 功能对比、性能、生态、结论 |
| 产品能力调研 | 产品能提供什么 | 功能、场景、用户流程、竞品 |
| 架构设计调研 | 如何落地    | 架构、模块、接口、资源管理 |
| 行业竞品调研 | 别人怎么做   | 产品能力、差异、优劣势   |
| 性能专项调研 | 性能瓶颈在哪里 | 测试方案、指标、数据、优化 |

## 五、调研报告的质量标准

一份合格的技术产品调研报告，不应该只是把官方文档重新整理一遍。

我建议用以下五个问题检查：

有没有讲清楚为什么要做？

业务背景、现存问题和建设目标。

有没有讲清楚技术是什么？

原理、架构、核心机制和执行流程。

有没有分析其他方案？

方案对比及选型依据，而不是直接给结论。

有没有讲清楚如何落地？

现有架构改造、模块设计、API、资源和生命周期。

有没有形成明确结论？

推荐方案、实施步骤、风险和待决策问题。

特别建议： 对你目前负责的强化学习云产品建设，报告应该重点放在第 4、5、6 部分，即技术架构、平台集成设计和实施方案。

veRL 和 Ray 的原理是技术基础，但最终汇报的核心应该是：

- 为什么选择 veRL，而不是其他框架？
- 为什么需要 Ray，Ray 和 Kubernetes 分别负责什么？
- 现有云平台需要增加哪些模块？
- Ray Cluster 在什么时机创建、如何复用、何时销毁？
- 如何分配和管理多节点 GPU？
- 如何完成训练、权重更新、Checkpoint 保存和模型交付？

这才是从技术调研走向云产品方案设计的关键。
